In short

  1. Compress the file as one deflate stream. On English text in 100-byte lines it measured ~3×. The whole file then crosses in ~25 s instead of ~75 s (model at 107 kbps, no loss), which leaves most of the 2 minutes to recover from attacks. The simulator, at 5 % loss, needs 27 s with compression and 71 s without.
  2. Selective-repeat ARQ with bursts of 16 frames and one bitmap ACK. Frames are delivered strictly in order, because only the first unbroken run of correct lines counts.
  3. Resume after any interruption. A HELLO handshake identifies the file, and the receiver keeps its progress, so an "attack" or a reboot costs seconds, not the round.
  4. Network Mode: gossip, not routing. Every node rebroadcasts the small file (~20 frames) on a randomised timer (Trickle-style). No addresses or positions are needed, and every node ends up with a copy (that is how teams win NM). It needs agreement with all teams.
  5. Specs: every interface has one file that defines it (Protocol specs). The NM interop spec is the one to share with the other teams.
  6. Software: our C code as one Linux program on the Raspberry Pi 3, started by systemd at boot. The radio loop runs in a real-time thread on its own core; USB, files and compression run in the main thread. The PC simulator runs the same protocol code, so it is tested before boards exist.

Frame formats

Each radio frame carries at most 32 bytes (nRF24 dynamic payload). A full DATA frame takes 1.32 ms on air at 250 kbps.

type|flags1 B
session1 B
seq2 B
compressed file bytes≤ 28 B
CRC2 B · radio

DATA, SRI/MRM. 32 B at most; the radio adds and checks the CRC (profile TEAM_250K). The 16-bit seq covers files up to 1.83 MB. session is a random byte chosen at HELLO, so frames from earlier runs or other teams are dropped.

type|flags1 B
session1 B
next_seq2 B
bitmap2 B
link1 B
CRC2 B · radio

ACK. next_seq = every frame before it has arrived. bitmap bit i = frame next_seq+1+i arrived. The last byte is for link logging: the nRF24 has no RSSI, so it carries the RPD bit (signal above about −76 dBm at the antenna).

type1 B
session1 B
file_len4 B
file_crc324 B
codec1 B
name≤ 21 B
CRC2 B · radio

HELLO (sender) and HELLO_ACK (receiver; replaces name with next_seq). They identify the file, so a rebooted receiver can resume where it stopped.

Type values (proposal): 0x01 DATA, 0x02 ACK, 0x03 HELLO, 0x04 HELLO_ACK, 0x05 END, 0x06 POLL (2 B: type, session; "repeat your ACK"), 0x4E NM_DATA. Flags: last-in-burst, retransmission. Definitions: proto/src/frames.h.

Link procedure (SRI and MRM)

sequenceDiagram
  participant TX as Sender (role switch = TX)
  participant RX as Receiver (role switch = RX)
  Note over TX,RX: GO: both buttons pressed
  loop until HELLO_ACK
    TX->>RX: HELLO(session, file_len, crc32, codec, name)
    RX-->>TX: HELLO_ACK(next_seq)  [0 on a fresh start, >0 on resume]
  end
  loop until the whole file is acknowledged or STOP
    TX->>RX: DATA × 16 (missing first, then new)
    RX-->>TX: ACK(next_seq, bitmap, rssi)
    opt ACK lost after a clean ACK
      TX->>RX: POLL
      RX-->>TX: ACK again (one short frame instead of 16)
    end
  end
  TX->>RX: END
  Note over RX: STOP: decompress what arrived in order, save to the SD card, then to USB

Timing

  • Burst of 16 × 32 B frames: ≈ 26 ms (1.32 ms each + 0.3 ms gap)
  • ACK + 2 radio turnarounds: ≈ 2.5 ms
  • ACK timeout: ≈ 11.6 ms at 250 kbps (scales with bit rate), then resend the burst
  • Goodput (model: 28 B of file per frame, 0.3 ms gap): ≈ 107 kbps on one channel, ≈ 96 kbps hopping with 10 % of hops busy

Resend rules

Each burst first resends every frame the last bitmap marked missing, then fills with new frames. The window never advances past a gap, so the receiver's output is always one continuous run.

If the last ACK showed a clean window, an ACK timeout most likely lost only the ACK: send a 2-byte POLL first, and resend the burst only if that times out too.

After 8 silent timeouts, send HELLO again with backoff. 250 kbps is already the nRF24's slowest rate, so there is no slower fallback. Never give up before STOP.

Recovering from attacks

Jamming or shadowing only looks like lost ACKs, and the retry loop covers it. A reboot of either box is handled by HELLO. The receiver keeps next_seq and the data on the SD card (fsync before it counts as committed), and the sender re-reads the file from the card.

Hardware watchdog through systemd (RuntimeWatchdogSec). A Linux reboot takes 10–30 s, not 0.3 s: simulator T19 (MRM, 30 s down) still delivers the file in 90.8 s. Target a boot of 10 s or less.

Network Mode: gossip proposal for all teams

No node knows its position, and the rules forbid a position switch. The file is only about 500 B, or 20 frames. So we suggest that nothing is routed: every node that holds part of the file rebroadcasts it on a randomised timer, following the Trickle algorithm (IETF RFC 6206), until STOP.

type 0x4E1 B
file_id2 B
idx1 B
total1 B
file bytes≤ 25 B
CRC-16 sw2 B

NM_DATA: the inter-team standard on the NM_COMMON radio profile. file_id = CRC-16 of the whole file. The radio's CRC protects each hop; the software CRC (CCITT-FALSE, big-endian) checks the data end to end across relays.

Link protocol: how the NM-file moves

sequenceDiagram
  participant O as Origin box (SW corner)
  participant S as Next box (South rim)
  participant C as Boxes further on (corner, East rim)
  participant R as Receiver (NE end)
  Note over O: Setup: NM-file from the USB stick to the SD card (usb_msc), cut into ~20 chunks of 25 B (≤ 64)
  Note over O,R: GO. Every box on RF_CH 77, 250 kbps, 10 mW, no chip ACKs, no addresses
  loop every Trickle interval I (random point in I/2..I, I = 1 s doubling to 8 s)
    O-)S: NM_DATA x 20 [0x4E, file_id, idx, total, 25 B, CRC-16]
  end
  Note over S: new chunk: check CRC-16, store it, log the time, reset I to 1 s
  S-)O: rebroadcasts what it holds (O hears duplicates and stays quiet after 3 copies per chunk)
  S-)C: the same frames reach one box further
  C-)R: relayed along the rim, with no routing
  Note over R: all chunks held and file_id = CRC-16 of the whole file: write the NM-file to the SD card
  Note over O,R: until STOP every box keeps gossiping, ever more slowly (I up to 8 s), so late boxes still catch up
  Note over O,R: STOP: every box writes the NM-file and NM_LOG.TXT to a USB stick (3 min)

flowchart LR
  RX["Frame heard on RF_CH 77"] --> V{"0x4E, CRC-16 ok,<br/>same file_id?"}
  V -- no --> X["drop, count it<br/>(bad CRC / other file)"]
  V -- yes --> N{"chunk new?"}
  N -- yes --> S["store it, log the time<br/>reset I = 1 s"]
  N -- no --> D["count a duplicate"]
  S --> F{"all chunks held and<br/>CRC-16(file) = file_id?"}
  F -- yes --> W["write the NM-file to the SD card"]
  T["Trickle timer fires<br/>(random in I/2..I)"] --> K{"3 copies per chunk<br/>heard this interval?"}
  K -- no --> B["broadcast every chunk held"]
  K -- yes --> Q["skip this turn"]
  B --> I2["I = min(2I, 8 s)"]
  Q --> I2

Behaviour

  • The sender (SW corner) starts with the whole file.
  • Every node keeps every valid chunk with the same file_id. When it hears its first new chunk, it starts rebroadcasting everything it holds.
  • Rebroadcast interval: random in [I/2, I], starting at I = 1 s and doubling up to 8 s. Skip a turn if 3 or more identical copies were heard in that interval.
  • Once all total chunks are held and the CRC-16 of the whole file equals file_id, the node writes the file to the SD card; otherwise it starts over. It saves the file to USB after STOP.

Why it fits

  • No addresses or positions, so it works in any random order of teams.
  • Every node ends up with a copy, which is the win condition. That makes the +2 bonus, and the +0.5 "poker bonus" for all teams, likely.
  • TX time: about 33 ms per full rebroadcast; in the simulator the busiest node transmits about 1.1 s in 5 min. No duty-cycle limit at 2.4 GHz.
  • Simple enough for every team to implement on any nRF24L01+ board.

MRM: every team hops

All teams transmit at the same time, 260 m apart. Since 16 Oct every team uses 20 dBm, which narrowband radios may only do while hopping, so every team hops with listen-before-talk (D-R6). Ours uses 37 channels (the even RF_CH 2–80, minus the three BLE advertising channels) in its own order (stride 7). There is no fixed channel plan any more.

  • The risk is a neighbouring team's box a few metres away: at 10 m it arrives 41 dB above our partner (47 dB at a two-ray peak), so hops landing within 4 MHz of each other collide (about 13 % of hop pairs). Pessimistic cost: ~31 % lost ACKs at the sender end, ~2 % lost data at the receiver end; even far apart, ~7 % of ACKs meet another sender on the same channel. Hence the POLL. Keep ≥ 10 m between teams' boxes, 30 m between senders (radio brief, MRM section).
  • Listen before talk with the RPD bit is now mandatory in SRI/MRM: the driver refuses to transmit on a hop without a clear check, and a busy hop is skipped.
  • Option B (only if Atenea Q11 says yes): the same 20 dBm on one fixed channel without hopping (profile TEAM_20DBM_FIXED, MRM plan 24 / 49 / 74 / 82). No hop clock or acquisition needed; the driver still demands a clear-channel check before every ≤ 10 ms of transmission (about 6 frames), so a 16-frame burst needs 3 checks. EN 300 328 limits non-hopping radios to 10 mW/MHz, which a narrow signal exceeds, hence the question.

Software ask: build the slot clock and hop acquisition early (bench by week 8), and keep the fixed-channel mode (Quick Mode, fallback) selectable at run time.

Linux pitfall: the scheduler. A stock kernel can pause our process for up to about 1.1 ms; the receiver's idle-ACK timer (~4 ms) and the TX_DS timeout (~3.8 ms) are tight against that. Use a PREEMPT_RT kernel, run the radio thread SCHED_FIFO on an isolated core (isolcpus=3, mlockall), set core_freq=250 so the SPI clock stays fixed, or widen both timers on Linux. Keep the root file system read-only (overlayfs) so a power cut or the drop test cannot corrupt the SD card. Test this early, because it is the classic way to lose a round.

Simulator: results on the nRF24 radio updated 17 Oct

  • collisions, and random or bursty loss;
  • a jamming blackout, and reboots.

It already caught a bug (on the old 868 MHz radio). With fixed timeouts, the 38.4 kbps fallback delivered only 883 lines. One frame (15.2 ms) outlasted the receiver's 15 ms idle-ACK timer, so the receiver ACKed in the middle of bursts and went deaf. All timeouts are now derived from the bit rate.

Still open in the simulator: an MRM scenario with four teams' boxes modelled explicitly (today their effect is a loss rate), and loss taken from measured packet-error rates instead of fixed percentages. Assumptions to measure on the Pi: 1 ms turnaround, 0.3 ms gap between frames (0.5 ms would give ~97 kbps; 1 ms gap and 2 ms turnaround ~73 kbps, still above the 67 kbps an uncompressed file needs).
